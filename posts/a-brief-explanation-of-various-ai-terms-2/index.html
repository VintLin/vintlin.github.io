一文理解各种 AI 名词（续）

2026年10月27日 · 36min ·中文

去年写完《一文理解各种 AI 名词》之后，本来以为短期内已经把常见的 AI 概念梳理得差不多了。没想到这两年 AI 领域的变化实在太快，大家不再满足于在网页聊天框里和大模型一问一答，而是开始把 Claude Code、Codex 这类桌面工具直接装进电脑里，让它们进到项目文件夹里真正下场干活。

随之而来的又是满天飞的新名词，什么 Token、CLI、Agent Skill、Plugin、Computer Use、AGENTS.md、LLM-Wiki、SubAgent、Worktree、Hook、Sandbox、Harness Engineering、Eval……听得人头又大了。所以最近我又花时间把自己的知识库笔记和看到的资料完整梳理了一遍，顺着上一篇的逻辑写了这篇续文，把这十组核心概念一个个拆开讲清楚。

大语言模型的底层补充

在上一篇文章的开头，我们讲到大语言模型的原理是“通过计算概率来预测下一个词”，并且提到可以通过调整 温度（Temperature） 来控制输出的创意性。在聊后面的新工具之前，我们先补上大语言模型最底层的三个概念——因为后面几乎所有的新技术，都是为了解决“上下文不够用”和“输出不稳定”这两个底层问题。

文字压缩——Token 与 Tokenizer

我们在聊天框里输入的是中文或英文，但大语言模型本质上是一个巨大的数学函数，它内部全是数字运算，根本不直接认识人类的文字。因此在我们和大语言模型之间，必须站着一位叫 Tokenizer（分词器） 的翻译官，负责把文字和数字互相转换。

流程如下：

  1. 切分：当你输入一句话（比如“我喜欢人工智能”），Tokenizer 会先按照常见的词组规律，把这句话切成一个个最小的文本碎片，每一个碎片就叫做一个 Token（比如切成“我”、“喜欢”、“人工智能”三个 Token）。

  2. 映射编码：Tokenizer 查阅自带的词表，把每一个 Token 转换成对应的数字编号（Token ID），变成一串数字列表（如 [2769, 4638, 912]）发送给大语言模型。

  3. 模型运算：大语言模型接收这串数字，在内部经过一通概率计算，预测出下一个最可能出现的数字编号。

  4. 解码还原：Tokenizer 再次登场，把模型吐出来的数字编号查表翻译回人类的文字，显示在你的屏幕上。

桌面大小——Context Window（上下文窗口）

理解了 Token，你就能立刻明白什么是 Context Window（上下文窗口）。

简单来说，Context 就是你发给大语言模型的所有输入内容（包括你的问题、历史对话、参考文档、可用工具列表等）；而 Context Window（上下文窗口） 则是指大模型单次最多能够处理的 Token 数量上限（比如 200K 或 1M 个 Token）。

你可以把 Context Window 想象成大语言模型面前的一张办公桌。哪怕现在的办公桌已经造得很大（能装下好几本书），在实际干活时我们依然会遇到三个非常现实的瓶颈：

  • 容量终归有限：一旦让 Agent 连续干活，几十轮的工具执行结果和文件内容很快就会把桌子堆满，超出上限的早期重要信息就会被丢弃。

  • 桌面太乱会让模型变笨：就算没超过桌子上限，如果你把几十页有用没用的资料一股脑全堆在桌上，模型也会被冗余信息干扰，抓不住重点，给出含糊其辞的回答。

  • 桌上的东西越多越贵：大模型的调用账单是按 Token 数量计费的，塞进上下文窗口的东西越多，每一次问答消耗的真金白银就越多。

理解了“这张办公桌既昂贵、又怕乱、还会满”，你就能看懂后面为什么大家都在拼命给上下文“瘦身”了。

选词开关——Temperature 与 Top-p

上一篇我们提到，模型为了保持创意，不会每次都死板地只选第一名，而是从最相关的几个词里随机挑选。这个挑选过程其实是由 Temperature（温度） 和 Top-p（核采样） 两个旋钮配合完成的。

流程如下：

  1. 生成分数：大语言模型先把词表里的几万个词扫一遍，给每个词打一个原始分数（专业术语叫 Logits）。

  2. Temperature 调节概率差距：系统通过函数把分数转换成百分比概率。这时 Temperature（温度） 负责调节高低分之间的差距：温度调得很低（如 0.1）时，第一名的概率优势会被放大到接近 100%，模型的回答就非常稳重保守；温度调高（如 1.0）时，各个词的概率差距被拉平，排在后面的词也有机会被选中，回答就更有创造力。

  3. Top-p 划定入围候选池：光调温度还不够，因为哪怕排在末尾的生僻词概率只有 0.01%，只要去抽签就依然存在被抽中的可能，一旦抽中整句话就乱套了。Top-p 的作用就是画一条入围分数线：比如把 Top-p 设为 0.9，系统就会把所有词按概率从高到低排好队，从第一名开始往后累加概率，一旦加到 90% 就立刻拉起警戒线，把后面那 10% 不靠谱的词全部踢出局，只在入围的前排词里随机抽签。

简单来说，Temperature 决定了前排候选词之间的概率差距有多陡，而 Top-p 决定了先把多少陪跑的冷门词直接淘汰掉。

解决工具调用与办事经验的问题

在上一篇文章里，我们介绍了让大模型调用外部工具的两种方式：模型端适配的 Function-Calling 和工具端适配的 MCP。

但当大家真正在日常工作里挂上好几个 MCP 服务之后，很快就发现了三个新痛点：第一，MCP 的工具说明书太占上下文窗口了；第二，光有工具不懂办事规矩，模型拿到了数据却不知道按什么流程处理；第三，有些软件根本没有提供 MCP 接口。为了解决这些问题，业界演进出了 CLI、Agent Skill、Plugin 和 Computer Use。

化繁为简——CLI（命令行工具）

CLI（Command Line Interface，命令行工具） 就是程序员平时在终端黑框框里输入命令来操作电脑的程序（比如用 git 管理代码、用 grep 搜索文本、用 ffmpeg 处理视频）。最近越来越多开发者在使用 Agent 时，开始减少接入笨重的 MCP，转而让大模型直接调用 CLI 工具。

为什么放着专门设计的 MCP 不用，反而用起命令行呢？因为 CLI 既省 Token，执行效率又高。

首先看 Token 消耗：如果你接入一个官方的 GitHub MCP 服务，它里面包含 44 个工具。为了让大模型知道有哪些工具可用，代理程序每次都要把这 44 个工具的名称、描述、参数格式全部塞进上下文窗口，光这份工具说明书就有 1,683 行，足足占掉 14,268 个 Token。而如果换成 CLI，代理程序只需要给大模型提供一个叫 bash（执行命令行）的工具，说明书只有十几行；至于 git、gh 这些常见命令怎么写，大模型在训练阶段早就学会了，根本不用你塞说明书教它。

再看执行效率，假设你的需求是“找出文件夹里所有的横版照片，加上水印，再上传到服务器”，CLI 的流程如下：

  1. 用户提出请求：用户告诉 Agent 批量处理横版照片并上传。

  2. 模型生成一行组合命令：大语言模型不需要分四五步调工具，而是利用命令行的管道符 | 和逻辑符 &&，直接生成一条串联命令（筛选横版照片 → 加水印 → 上传服务器），发给代理程序。

  3. 本地一次性跑完：代理程序在本地终端里一口气把这三步全部自动跑完，中间过程完全不需要绕回大模型去思考。

  4. 返回最终结果：等所有照片上传完毕，代理程序只把最后“执行成功”的简短结果发回给大语言模型，模型再向用户汇报完成。

当然，MCP 也并没有被淘汰。因为 CLI 什么命令都能敲，万一文件名带了特殊引号容易报错，甚至万一模型失手敲出删除命令（rm -rf）就会闯祸；而 MCP 采用结构化的 JSON 传参，只能执行开发者允许的固定操作。因此：追求轻快省钱的个人与本地环境越来越偏爱 CLI，而追求安全可控的企业与云端环境依然离不开 MCP。

按章办事——Agent Skill（技能包）

不管是用 MCP 还是 CLI，它们解决的都只是“怎么拿数据、怎么调软件”的问题。但在真实工作里，我们往往有一套特定的办事规矩：比如写会议总结必须按“参会人员、议题、决定”的格式输出；聊到采购预算时必须核对《集团财务手册》；写完后还要运行脚本上传服务器。

为了不把这些规矩每次都重复粘贴一遍，Anthropic 推出了 Agent Skill（技能包），并迅速成为了各大 AI 工具支持的通用标准。

用最通俗的话讲，Agent Skill 就是一个放在特定文件夹里、供大模型随时翻阅的“办事说明文档（SKILL.md）+ 配套资源包”。它最精妙的设计叫做渐进式披露（按需加载），把信息分成了三层，用多少拿多少：

  • 第一层：元数据层（Metadata，常驻目录）：SKILL.md 文件最开头的几行只写这个技能的名称（name）和一句话描述（description）。平时大模型只能看到这一层，哪怕你装了十几个 Skill，占用的空间也只相当于一页薄薄的目录。

  • 第二层：指令层（Instruction，按需加载的正文）：SKILL.md 剩下的正文部分，详细写着办事步骤和输出模板。只有当大模型觉得当前任务用得上这个 Skill 时，才会把它读进上下文。

  • 第三层：资源层（Resource，按需中的按需）：文件夹里还可以附带两样东西：一是 Reference（参考资料），比如长篇的 集团财务手册.md，只有会议内容真的聊到“花钱”时才会去读取，平时躺在硬盘里不占一个 Token；二是 Script（可执行脚本），比如写好的 upload.py 上传代码，代理程序只会直接运行它拿结果，根本不会把代码内容读进大模型脑子里，哪怕脚本有一万行，消耗的上下文也是零。

使用 Agent Skill 的完整流程如下：

  1. 发送请求与目录：用户发送“帮我总结这段会议录音并上传”，代理程序把请求连同所有 Skill 的名称和一句话描述（第一层目录）发给大语言模型。

  2. 命中并加载正文：大模型扫了一眼目录，发现这件事归“会议总结助手”管，于是通知代理程序读取对应的 SKILL.md 正文（第二层指令）发给自己。

  3. 按条件查阅参考资料：大模型按照正文规矩总结时，发现录音里提到了订酒店的费用，触发了财务规则，于是请求读取 集团财务手册.md（第三层 Reference），核对后在总结里加上财务超标提醒。

  4. 直接执行脚本：总结写好后，大模型按照规则通知代理程序直接运行文件夹里的 upload.py 脚本（第三层 Script），完成服务器上传。

  5. 返回最终结果：代理程序将总结正文和上传成功的信息展示给用户。

一键安装——Plugin（插件）

当你陆陆续续攒了好几个好用的 Agent Skill、配好了对应的 MCP 工具、还设置了自动化规则之后，如果你想把这套“前端设计工作流”或“数据分析工作流”分享给同事，让他自己去一个个建文件夹、配环境还是太折腾了。

于是就有了 Plugin（插件）。你可以把 Plugin 想象成电脑上的 .dmg 或 .exe 全家桶安装包：它把完成某一个领域任务所需的 Agent Skill（办事手册）、MCP（外部工具连接器）、SubAgent（子代理）和 Hook（自动化钩子） 全部打包在一起。

流程如下：

  1. 开发者打包：开发者把配好的一整套 Skill、MCP 配置和预设规则封装成一个 Plugin 发布到插件市场。

  2. 用户一键安装：用户在自己的 Agent 工具（如 Claude Code 或 Codex）里打开插件目录，选中需要的插件点击安装。

  3. 自动挂载能力：代理程序自动将插件里包含的所有工具、技能目录和配置注册就绪，无需人工手动配置。

  4. 直接投入使用：用户直接开口提需求，Agent 就能立刻调用插件里的全套工具和办事流程完成任务。

看着屏幕干活——Computer Use（电脑操控）

前面不管是 Function-Calling、MCP 还是 CLI，都有一个共同前提：目标软件得提供接口或者命令行。可现实中有很多老旧的办公软件、网页后台或者桌面程序，既没有开放接口，也不能用命令行操作，这时候该怎么办呢？

这就催生了 Computer Use（电脑操控，也常被称为 GUI Agent）。它的思路非常直接：既然没有内部通道，那就让大模型像真人一样“用眼睛看屏幕、用手移动鼠标和敲键盘”。

流程如下：

  1. 用户下达指令：用户提出请求，例如“帮我在某个没有接口的后台系统里填报今天的表单”。

  2. 截取当前屏幕：代理程序直接对当前电脑桌面或浏览器窗口截一张图，发送给具备视觉理解能力的大语言模型。

  3. 视觉定位与决策：大语言模型像人眼一样看图分析，找到“输入框在屏幕坐标 (x=420, y=310) 的位置”，并生成下一步的操作指令（如“移动鼠标到该坐标点击，并输入文字”）。

  4. 操控虚拟键鼠：代理程序调用操作系统的底层接口，控制虚拟鼠标移过去点击、用虚拟键盘敲入文字。

  5. 再次截图确认：操作完成后，代理程序再截一张最新的屏幕画面发给大模型，模型确认填报成功后再继续下一步，直到任务全部完成。

Function-Calling vs MCP vs CLI vs Agent Skill vs Plugin vs Computer Use

这六个和“动手干活”有关的名词放在一起很容易混淆，我们不妨用“请一位厨师来餐厅后厨干活”来打个比方，一下子就清楚了：

  • Function-Calling（函数调用）：是厨师具备的基础沟通本能——懂得“开结构化单子去调用外部设备”，而不是只会站在原地跟你清谈。

  • MCP（模型上下文协议）：是后厨墙上的统一标准插座与供货通道——不管连的是外部数据库还是第三方软件，插上就能安全可控地把食材（数据）取进来。

  • CLI（命令行工具）：是厨师随手拎着的轻便瑞士军刀——在本地熟悉的操作台上，不用走繁琐的外部协议，切菜、串菜（管道 |）一行命令当场搞定，省空间又极快。

  • Agent Skill（技能包）：是压在案板下的招牌菜标准菜谱（SOP）——正如 Anthropic 所说，“MCP 把模型连接到数据，而 Skill 教模型拿到数据后怎么干活”，而且平时只看菜名目录，点到哪道菜才翻哪一页。

  • Plugin（插件）：是总部发给分店的一键开业大礼包——把配好的供货接口（MCP）和成套菜谱（Skill）装进一个箱子里，一键安装就能直接开张。

  • Computer Use（电脑操控）：则是当遇到一台没有任何智能接口的老式灶台时，厨师直接用眼睛看着仪表盘、亲手去拧旋钮和按键的兜底本事。

解决跨对话失忆与知识沉淀的问题

当 Agent 学会了用工具和看菜谱之后，一旦我们和它日复一日地合作同一个长期项目，第二个大痛点就冒出来了：为什么每次新开一个对话窗口，我之前交代过的项目规矩它就忘得一干二净？为什么给它塞了几百篇资料，它还是没法把知识攒下来？

这就需要用 AGENTS.md / CLAUDE.md 和 LLM-Wiki 来改造 Agent 的记忆与知识库。

立下家规——AGENTS.md / CLAUDE.md（项目规则文件）

在上一篇里我们讲过，Agent 拥有长期记忆（Memory），现在很多 AI 软件也会在后台自动记住你的习惯。但很快大家就发现，光靠软件自带的 Memory 根本管不住严肃的项目开发。

因为自动 Memory 记下的大多是你聊天时流露出的隐式偏好（比如“我习惯用中文”、“我喜欢简短的回答”），它是系统在后台悄悄总结的，你很难核对它到底记全了没有。而在项目开发里，有很多规矩是“一旦违反就会惹祸”的（比如“不准主动提交 git”、“写代码前必须先画草图确认”、“运行测试用哪条命令”）。

为了立下铁打的显式规矩，业界形成了一个新习惯：在项目文件夹的根目录下，放一个叫 AGENTS.md（在 Claude Code 里叫 CLAUDE.md）的文档。

流程如下：

  1. 编写项目目录与家规：开发者在项目根目录下创建 AGENTS.md，写明本项目的核心禁令、常用命令，以及各个详细文档存放在哪个子文件夹里。

  2. 启动时自动加载：每当用户在这个项目里新开一个对话窗口，代理程序都会在后台自动读取这份 AGENTS.md，把它作为默认背景连同用户的问题一起发给大语言模型。

  3. 按图索骥查细节：这里有一个来自 OpenAI 实战的重要经验——千万不要把所有资料塞进一个几千行的超大 AGENTS.md 里（就像新员工入职第一天直接砸给他一本字典厚的员工手册，模型反而抓不住重点，文档也很快会过时）。最科学的做法是把 AGENTS.md 控制在 100 行左右，只当成一张导航地图，大模型看完地图后，需要改哪块再去读对应文件夹里的详细文档。

  4. 随项目共同演进：每当 Agent 在项目里犯了一次典型的错误，开发者就把这条避坑规则补进 AGENTS.md 里并随代码库保存。从此以后，无论是你还是团队同事新开对话，Agent 都绝不会再犯同一个错误。

读书做笔记——LLM-Wiki（编译型知识库）

在上一篇里，我们介绍了用 RAG（检索增强生成） 来查外部知识库。但用久了你会发现，传统 RAG 有一个天生的局限：它每次都是在“临时翻原书”，完全没有“做笔记积累”的过程。

比如你往向量数据库里丢了 100 篇行业文章，每次你提问时，RAG 都是临时去把这 100 篇文章切成的碎片搜一遍，捞出最相似的几段塞给模型；等这次回答结束，刚才好不容易梳理出来的脉络就消失了，下次提问还得从零去捞碎片。

为了解决这个痛点，前特斯拉 AI 总监 Andrej Karpathy 提出了一种全新的知识管理模式——LLM-Wiki（编译型知识库）。它的核心理念是：用文件系统代替向量检索，让大模型平时就像人类学者做卡片笔记一样，先把原始资料“编译”成结构化的知识卡片库。

流程如下：

  1. 收集原始资料（Raw Sources）：用户把收集到的文章、会议记录或论文放进只读保存的原始资料文件夹中。

  2. 消化与编译（Ingest）：大语言模型通读原始资料，按照预设的整理规则（Schema），把里面的核心概念、论证逻辑和事实提炼成一张张结构清晰的 Markdown 笔记页面（Wiki 层），并用双向链接 [[...]] 把新卡片和已有的旧卡片串联起来。

  3. 按导航链查询（Query）：当用户需要写文章或做分析时，Agent 不需要去海量碎片里盲目检索，而是直接顺着 Wiki 的“主题入口 → 核心问题 → 观点卡片”读取已经编译好的高密度知识。

  4. 定期健康检查（Lint）：每隔一段时间，让脚本和模型自动巡检整座知识库，修复断掉的链接、合并重复的卡片、更新过时的结论，让知识库越用越扎实。

Memory vs AGENTS.md vs RAG vs LLM-Wiki

把这四个和“记忆与知识”相关的词放在一起对比，它们在 Agent 系统里的分工就一清二楚了：

  • Memory（自动记忆）：像老搭档在日常相处中摸清的隐式个人习惯（比如你爱喝什么口味的咖啡、喜欢什么样的汇报语气），省心但不够精确。

  • AGENTS.md / CLAUDE.md（项目规则文件）：像贴在工作室墙上的显式家规与科室地图，每次进门必看，专门管那些“绝对不能做错”的纪律和去哪找资料的路线。

  • RAG（检索增强生成）：像开卷考试时手边放着的几十本厚词典，平时不读，遇到具体问题时按关键词临时翻出几段参考，适合应付几万条客服问答、海量接口文档这类大而杂的资料。

  • LLM-Wiki（编译型知识库）：则像你平时花功夫读完十本书后，亲手整理出来的结构化读书笔记与错题卡片盒，知识在入库时就已经被消化、串联好了，随翻随用，越攒越厚。在实际工程里，这四者常常是互相配合使用的。

解决长任务混乱与失控的问题

当 Agent 有了趁手的工具（CLI / MCP）、有了办事手册（Skill）、也有了家规和知识库（AGENTS.md / Wiki），我们自然会放心大胆地把越来越长、越来越复杂的任务交给它。但紧接着，最让人头疼的场面就出现了：

一是上下文被中间废料撑爆了（比如让它审查一个大项目，读了几十个文件后主对话直接卡死变笨）；二是多个任务并行时互相踩脚（两个 Agent 同时改同一份文件直接撞车）；三是模型不听劝乱跑（忘了家规或者误删重要文件）。

为了解决这三个问题，业界搬出了四件工程利器：SubAgent、Worktree、Hook 和 Sandbox。

派分身干活——SubAgent（子智能体）

前面我们聊过 Agent Skill，但 Skill 有一个硬伤：它是在你当前的主对话窗口里执行的。如果你让 Skill 去排查一个有几万行代码的项目故障，它翻看的每一个文件、每一行报错日志都会塞进你的主对话上下文里，很快就会把主对话撑爆。

为了保护主对话的“桌面”干净，我们引入了 SubAgent（子智能体）。它其实就是一个拥有自己独立的上下文窗口、独立的工具列表和独立 Skill 的分身 Agent。

流程如下：

  1. 主 Agent 接收并拆解任务：你在主对话里提出“帮我全面排查一下项目里的安全隐患，并修改登录页样式”。主 Agent 判断“排查安全隐患”需要翻看大量文件，于是决定召唤专门负责代码审查的 SubAgent。

  2. 开辟独立小房间干活：代理程序为这个 SubAgent 开启一个全新的独立对话窗口（甚至可以限制它只有“只读权限”，防止它乱改文件）。SubAgent 在自己的独立窗口里翻阅了 50 个文件、做了大段中间分析，这些过程全都留在它自己的小房间里，绝不占用主对话的一个 Token。

  3. 只向主对话汇报结论：当 SubAgent 排查完毕后，它的独立窗口任务结束，只把最后浓缩出的几十行审查结论交给主 Agent。

  4. 主 Agent 汇总推进：主 Agent 拿着干干净净的结论继续帮你修改登录页样式，整个主对话始终保持清爽敏捷。

因此，Agent Skill 与 SubAgent 最大的区别就在于对上下文的处理方式：需要结合当前聊天背景、且不怎么占地方的活（比如写每日总结），交给 Skill 在主窗口里干；而相对独立、且中间过程会产生大量垃圾信息的活（比如全库搜索、独立代码审查），就派 SubAgent 去隔壁房间干。

隔离工作间——Worktree（独立工作区）

有了分身之后，你可能希望让两个 Agent 同时干活：一个去开发新功能，另一个去修老 Bug。但如果它们俩在同一个项目文件夹里同时修改代码，你改一半、我改一半，文件立刻就会互相覆盖冲突。

为了解决这个问题，现在的桌面 Agent（如 Codex、Claude Code）引入了 Git 的 Worktree（独立工作树 / 独立工作区） 机制。

流程如下：

  1. 发起并行任务：用户同时派发两个修改代码的任务，并选择在 Worktree 模式下运行。

  2. 创建隔离目录副本：代理程序在后台自动基于当前项目，复制出两个相互独立的 Worktree 文件夹和分支。

  3. 各自在平行时空修改：两个 Agent 分别进到各自的 Worktree 文件夹里改代码、装依赖、跑测试，两边的文件完全隔离，谁也不会踩到谁的脚。

  4. 审查与合并：等两边都干完活并通过测试后，用户检查无误，再把改动一键合并回主项目，并归档清理掉临时的 Worktree 目录。

强制触发器——Hook（钩子）

即便我们在 AGENTS.md 里写好了“每次改完代码必须格式化”、“千万别删生产配置”，大语言模型毕竟是个概率模型，忙中出错或者忘了规矩是常有的事。

怎么把“请模型自觉记住”变成“百分之百强制执行”？这就用到了 Hook（生命周期钩子）。它允许开发者在“工具使用前（PreToolUse）”、“工具使用后（PostToolUse）”或“任务结束时”等固定节点，设置一段由系统自动运行的程序逻辑。

流程如下：

  1. 配置触发时机与规则：用户在配置里设定好 Hook，比如“每当模型使用 Edit（编辑文件）工具之后，自动运行代码格式化命令”，或者“每当模型使用 bash 工具之前，检查命令是否包含高危删库操作”。

  2. 事前硬拦截（PreToolUse Hook）：当大语言模型生成了一条调用命令发给代理程序时，如果触发了事前 Hook 的禁令（例如试图强推代码或修改 .env 密钥），Hook 会在命令执行前直接将其拦下并报错，根本不给模型闯祸的机会。

  3. 事后自动执行（PostToolUse Hook）：当模型顺利编辑并保存了一个代码文件后，事后 Hook 立刻在后台自动运行格式化工具和语法检查（Linter）。

  4. 异常自动打回：如果 Hook 跑检查时发现了语法错误，代理程序会直接把报错信息塞回给大语言模型，逼着它当场修好才能继续往下走。

安全隔离笼——Sandbox（沙盒）

除了用 Hook 盯住单个操作之外，为了防止大模型在执行命令行（CLI）或运行脚本时把你的电脑系统搞坏，代理程序还会在最外层套上一个 Sandbox（安全沙盒）。

你可以把 Sandbox 想象成操作系统给 Agent 划定的物理隔离笼。在沙盒开启的状态下：

  • 限制文件读写范围：规定 Agent 只允许读写当前这一个项目文件夹里的文件，外面的系统目录、桌面私人文件一律碰不到。

  • 限制网络与系统权限：规定 Agent 不能随意向未知的外部服务器发送数据，也不能修改电脑的系统级设置。

这样一来，哪怕大模型在某个瞬间出现了严重幻觉，或者读到了别人藏在网页里的恶意诱导指令，它折腾出来的最大破坏也被死死锁在沙盒这口笼子里，不会伤及你的电脑和生产环境。

给 Agent 套上缰绳与验收——Harness 与 Eval

把前面讲到的所有组件（AGENTS.md、工具、Skill、SubAgent、Worktree、Hook、Sandbox）全部拼在一起，我们就终于走到了当下 AI 领域最重要的一组系统概念：Harness Engineering（挽具工程） 与 Eval（评测验收）。

套上缰绳——Harness Engineering（挽具工程）

Harness 这个单词的本意是套在马身上的马具（包括缰绳、马鞍、笼头等）。

为什么要拿马具来比喻呢？因为今天的大语言模型就像一匹力大无穷的千里马，能干的事情太多了；但如果你不给它套上马具、任由它脱缰狂奔，它很快就会偏离跑道、重复犯错，根本没法稳定交付结果。因此，在 Agent 系统里，用来控制、引导和约束大语言模型的整套外围系统，就叫做 Harness。

业界用了一个非常巧妙的公式来定义它：

Harness = Agent - Model（或者写为：Agent = Model + Harness）

也就是说，一个完整的 Agent 减去最核心的大语言模型，剩下的所有东西全都是 Harness。而 Harness Engineering（挽具工程），就是一门专门研究“除了大模型本身不研究，其他外围系统全都要研究”的工程技术。

在 OpenAI 用 AI 自主编写近百万行代码的实战分享中，一个成熟的 Harness 工程主要围绕三件事运转：

  1. 提供结构化的信息环境：把分散在聊天记录或人脑子里的规则统一搬进代码仓库，并用 100 行左右的轻量级 AGENTS.md 做好目录导航，让 Agent 随时能查到准确的背景知识。

  2. 构建自动验证与反馈闭环：给 Agent 配齐浏览器调试器、日志查看器、架构检查器（Linter）和自动化测试。Agent 每改完一处代码，系统立刻自动检测并把报错反馈给它，让它“自己看到问题、自己原地修复”，直到所有检查全绿为止。

  3. 后台定期清理技术债：因为 AI 大量写代码难免会留下重复代码或过时文档，Harness 系统还会配置后台定时任务（Automation），每天像扫地机器人一样自动扫描全库，把偏离规范的代码和过时的文档自动修正提交。

到了这一步，人类工程师和 AI 的关系就彻底变成了：“人类负责掌舵，Agent 负责干活（Humans steer, agents execute）”——人不再亲自去写每一行琐碎的代码，而是专门负责设计这套“马具系统”，让 Agent 在跑道里安全狂奔。

独立质检员——Eval（评测）

虽然 Harness 能让 Agent 跑得很稳，但在任务结束交工的那一刻，还有一个致命的陷阱：千万不能只让干活的 Agent 自己评价自己的成果。

Anthropic 在实验里发现，如果让同一个 Agent 既负责写代码、又负责给自己打分验收（自评），本质上就是“王婆卖瓜，自卖自夸”——模型对自己写出来的东西天然带有滤镜，哪怕界面布局乱成一团、功能还有明显 Bug，它也会粗略看一眼就自信满满地宣布“完美收工”，甚至有时为了通过测试，偷偷把报错的测试题给删掉。

为了彻底解决“自评护短”的问题，必须引入独立的 Eval（Evaluation，质量评测机制），把“干活的人”和“验货的人”拆开。在 Anthropic 的经典三角色架构里，完整流程如下：

  1. Planner（规划者）拆解清单：用户提出一句话需求后，先由 Planner Agent 把这句模糊的需求拆解成一份详尽的功能点列表。

  2. Generator（生成者）对齐标准：负责干活的 Generator Agent 领到功能点后，先不急着动手，而是先和负责验收的质检员讨论商定“这个功能到底做到什么程度才算合格”的交付标准。

  3. Generator 动手实现：标准对齐后，Generator 开始调用工具编写代码实现功能，并在完成后提交给质检员。

  4. Evaluator（独立评估者）挑刺验收：作为独立第三方的 Evaluator Agent（这种让独立大模型按标准打分挑刺的方式也叫 LLM-as-a-Judge）绝不替生成者护短，它会严格用自动化工具和交付标准去检验成果。

  5. 打回重修直至通过：只要 Evaluator 发现不达标，就会列出问题清单打回给 Generator 重新修改；两边循环往复，直到独立质检员真正点头放行，才算完成交付。

而在日常衡量一个 Agent 系统到底靠不靠谱时，Eval 还会区分两个常用指标：pass@k（尝试 k 次只要成功 1 次就算过，用来看模型的能力上限与灵感）和 pass^k（连续运行 k 次必须每一次都成功，用来看系统能不能真正放心上线的稳定性）。

提示词工程 vs 上下文工程 vs 挽具工程

最后，我们把从上一篇文章延续到这一篇的三个“工程”放在一起做个总结对比，你就能看清这几年 AI 技术演进的全景主线了：

  • 提示词工程（Prompt Engineering）：核心是“怎么问问题”。它只关注单次发给大模型的那一句话怎么写得更清楚、更准确。

  • 上下文工程（Context Engineering）：核心是“怎么给信息”。它把关注点扩大到了模型的整个输入窗口（Context Window），研究怎么通过检索选择、按需披露和上下文压缩，在恰当的时机把最有用的背景资料喂给模型。

  • 挽具工程（Harness Engineering）：核心是“怎么搭系统”。它直接跳出了文本输入的范畴，把模型外围的规则地图（AGENTS.md）、技能手册（Skill）、分身隔离（SubAgent / Worktree）、强制护栏（Hook / Sandbox）以及独立质检闭环（Eval）组装成一整套运行环境，让大模型这匹千里马真正能拉着马车跑完长途。

Harness Engineering挽具工程，研究如何围绕大模型搭建整套外围运行与控制系统（Harness = Agent - Model），实现“人类掌舵，Agent 干活”。
Eval（评测）独立的质量验收机制，通过将生成者（Generator）与独立评估者（Evaluator / LLM-as-a-Judge）分离，并用 pass@k 与 pass^k 衡量可靠性，确保交付质量。
